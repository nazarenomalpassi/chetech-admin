CONTINUATION: operations amendments, full history and safe drafts
This section supersedes the earlier limitations about reopening, labelled list caps
and missing visit drafts. The first migration file was NOT changed; its SHA256 remains

Additional implementation
- Reopening appends an immutable amendment linked to the original closure. Correcting
  the reopened physical count appends the next immutable close with a required reason.
  Actor/time, linkage and every original count remain inspectable. Unique successor
  indexes prevent concurrent forks. DB validation prohibits changing expected historical
  balances; reopening preserves the whole previous count. No ledger/payment/balance writes.
- Historical corrections use the original expected snapshot, NOT today's getCashData.
  Reopening/correction are admin-only, idempotent by request UUID and guarded by head ID.
  Cash history also has server pagination so old days can be corrected.
- Visits now count before fetching a 25-row server page, clamp stale page numbers, and
  use a stable date/time/ID order. Date/day/week, status and technician filters survive
  paging and saves. Counters are explicitly labelled as page-local.
- Outsourcing uses a read-only, security-invoker operations RPC with 25-row pages and
  complete filtered counts. Search across linked REP/customer/device data is applied
  before paging and treats wildcard characters literally. Day/week filters and all
  statuses (including cancelled) apply to the complete retained history, not 200 rows.
  The RPC reads linked repair data under existing caller RLS; it does not edit orders.
- Visit drafts are schema-whitelisted, user/visit isolated, per-tab sessionStorage,
  expire after 24 hours and are recovered only on explicit request. Other-user drafts
  are removed when an account changes on the shared tab. Stale edit drafts are readable
  but cannot be applied over a newer server version. Browser storage failure is surfaced.
  Saves acknowledge a specific draft generation; old receipts cannot erase a newer draft.
  Admin edits require the original updated_at token. Technician UI submits that token
  too. A unique operation UUID prevents duplicate new visits after a lost save response.
